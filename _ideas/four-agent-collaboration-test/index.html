The Four-Agent Collaboration Test

How we built, tested, and redesigned a four-agent AI collaboration system over two days — and what it taught us about where the boundaries between AI roles actually belong.

Status First Draft Complete
First built July 2026
Domain AI Collaboration, System Design
Collaborator Gemma 4 12B (Google) via Ollama in Open WebUI

The Experiment

On July 2nd, I put a four-agent system to the test. The goal was simple but foundational: see if we could build a collaborative pipeline where AI agents interacted with each other autonomously, mediated by a shared "Messages" folder as their primary communication channel.

We were testing several core capabilities:

  1. Could each agent read from and write to the Messages/ directory using specific naming conventions?
  2. Did they understand their own boundaries (Draft vs. Publish)?
  3. Did they grasp the full workflow, including the handoff logic for subsequent deployment?
  4. Most importantly, could they pass a "baton" to one another without me manually intervening as a bridge?

The Four Collaborators

The team consisted of four distinct agents, each fulfilling specific roles in the loop:

  • Cowork: (Claude via the Cowork app) serving as a Draft Agent.
  • Claude Code: (Claude via CLI) serving as our Publish Agent and technical reviewer.
  • AnythingLLM: (Gemma 4 12B locally) acting as an alternative Draft Agent.
  • OpenCode: (a local model) serving as an alternative Publish Agent and independent auditor for check-and-balance verification.

What Passed

The core architecture held up remarkably well. Every agent successfully interacted with the Messages/ folder, following the required naming conventions to ensure a persistent, auditable record of every exchange.

Additionally, the "check-and-balance" process proved highly effective; when Cowork and Claude Code double-checked one another's work, they caught errors in system prompt design and architectural decisions that other agents had overlooked. The Messages/ folder successfully functioned as a robust inter-agent bus.

What Failed

Two specific requirements were flagged during the verification:

  1. Connectivity Gap: AnythingLLM produced responses that looked correct but were hallucinated from training data because the actual file system tools weren't connected to its workspace. It didn't "know" it couldn't see the files; it just wasn't told it had a chance.
  2. The HTML Ceiling: Even when switched to Open WebUI, Gemma 4 hit a hard wall with HTML generation. Despite multiple prompt variations and explicit instructions, it consistently failed to maintain div scope for multi-card layouts — wrapping every card individually rather than wrapping the group.

The Diagnosis

These weren't just "bad prompts." They were two different types of problems:

  1. Configuration Issue: AnythingLLM's failure was purely environmental. The tools weren't connected to the workspace, so it defaulted to its internal weights.
  2. Model Capability Limit: Gemma 4's failure with HTML was a structural ceiling. No amount of instruction-tuning solved the problem of maintaining complex nested structures in large blocks of code.

The Fix

The solution was architectural, not instructional. We redefined the boundary between roles:

The Draft Agent is now restricted to producing structured Markdown only — no HTML, no CSS, and no frontmatter. It provides a "clean" content file with a standardized header.

The Publish Agent (specifically Claude Code) takes that Markdown and handles the conversion to valid HTML using our established production specs.

By decoupling content from presentation, we removed the requirement for any single model to be an expert in both, effectively bypassing the technical limitations of smaller or less-consistent models while maintaining a high standard for the final output.

Why This Matters

This evolution confirms that AI-agnostic collaboration is possible when you design for where the boundaries naturally lie.

By using the Messages/ folder as a shared record, every interaction remains auditable and transparent. By separating content from markup, we ensure that the Draft Agent role is genuinely portable — any model capable of writing in my voice can fulfill its purpose regardless of its ability to manage complex CSS nesting. The failures on July 2nd weren't wasted time; they revealed the ceiling of instruction-based "fixes" and led us to a more robust, scalable architecture.
