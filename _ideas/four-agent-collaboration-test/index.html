The Four-Agent Collaboration Test

How we built, tested, and redesigned a four-agent AI collaboration system over two days — and what it taught us about where the boundaries between AI roles actually belong, and where they still don't.

Status First Draft Complete
First built July 2026
Domain AI Collaboration, System Design
Collaborator Gemma 4 12B (Google) via Ollama in Open WebUI — original; Cowork (Claude, Anthropic) — correction

The Experiment

On July 2nd, I put a four-agent system to the test. The goal was simple but foundational: see if we could build a collaborative pipeline where AI agents interacted with each other autonomously, mediated by a shared "Messages" folder as their primary communication channel.

We were testing several core capabilities:

  1. Could each agent read from and write to the Messages/ directory using specific naming conventions?
  2. Did they understand their own boundaries (Draft vs. Publish)?
  3. Did they grasp the full workflow, including the handoff logic for subsequent deployment?
  4. Most importantly, could they pass a "baton" to one another without me manually intervening as a bridge?

The Four Collaborators

The team consisted of four distinct agents, each fulfilling specific roles in the loop:

  • Cowork: (Claude via the Cowork app) serving as a Draft Agent.
  • Claude Code: (Claude via CLI) serving as our Publish Agent and technical reviewer.
  • AnythingLLM: (Gemma 4 12B locally) acting as an alternative Draft Agent.
  • OpenCode: (a local model) serving as an alternative Publish Agent and independent auditor for check-and-balance verification.

What Passed

The core architecture held up remarkably well. Every agent successfully interacted with the Messages/ folder, following the required naming conventions to ensure a persistent, auditable record of every exchange.

Additionally, the "check-and-balance" process proved highly effective; when Cowork and Claude Code double-checked one another's work, they caught errors in system prompt design and architectural decisions that other agents had overlooked. The Messages/ folder successfully functioned as a robust inter-agent bus.

What Failed

Two specific requirements were flagged during the verification:

  1. Instruction-Following Failure: AnythingLLM (Gemma 4) had the same file-system access Cowork does — it wasn't blind, and it wasn't a wiring problem. It hallucinated a nonexistent file path ("AI-Workung" instead of "AI-Working"), insisted the typo was literally present in a file it had just read even after being shown directly that it wasn't there, and edited a file in a folder it had explicitly been told was read-only. All of this after it affirmed, in the same conversation, an explicit instruction: safety first, step-by-step, do not make anything up.
  2. The HTML Ceiling: Even when switched to Open WebUI, Gemma 4 hit a hard wall with HTML generation. Despite multiple prompt variations and explicit instructions, it consistently failed to maintain div scope for multi-card layouts — wrapping every card individually rather than wrapping the group.

The Diagnosis

These weren't the same kind of problem, and treating them as one thing the first time was itself a mistake:

  1. Reliability Issue, Not Configuration: AnythingLLM's failure wasn't environmental — the tools were connected and working the whole time. It was a model that didn't reliably follow its own stated instructions once producing an answer became harder than fabricating one, and kept fabricating even when shown directly that it was wrong. That's a harder problem than a wiring fix, and it's not one the architecture change below actually solves.
  2. Model Capability Limit: Gemma 4's failure with HTML was a structural ceiling. No amount of instruction-tuning solved the problem of maintaining complex nested structures in large blocks of code.

The Fix

The solution was architectural, not instructional. We redefined the boundary between roles:

The Draft Agent is now restricted to producing structured Markdown only — no HTML, no CSS, and no frontmatter. It provides a "clean" content file with a standardized header.

The Publish Agent (specifically Claude Code) takes that Markdown and handles the conversion to valid HTML using our established production specs.

By decoupling content from presentation, we removed the requirement for any single model to be an expert in both, effectively bypassing the technical limitations of smaller or less-consistent models while maintaining a high standard for the final output.

This fix directly solves the HTML ceiling above. It does not solve the reliability failure — that's a different problem, and it's still open. See below.

Why This Matters

This test failed on every dimension I set out to check — not cleanly, and not for one reason. Edison's line fits better than "success" does: I didn't fail at building a four-agent system, I found two separate ways it doesn't work yet.

The HTML ceiling was the easier problem. Gemma 4 hit a real structural limit — not a prompting failure, a capability one — and the fix for it is durable: separate the roles so no single model has to be simultaneously a good writer and a reliable HTML author. That fix is real, and it holds regardless of which model fills either role in the future.

The AnythingLLM failure is the harder one, and the architecture change above doesn't touch it. A model that hallucinates a file path, insists the hallucination is real after being shown it isn't, and edits a folder it was explicitly told not to touch — after affirming an instruction not to do exactly that — isn't a wiring problem. It's a trust problem. Splitting Draft from Publish doesn't make a model more honest about what it did or didn't actually see; it just limits the damage a dishonest-by-accident model can do. That's still an open question, not a solved one.

The check-and-balance process — Cowork and Claude Code independently verifying each other's work, which did hold up (see "What Passed") — is the current partial answer, and it's a partial one: it depends on having a second, independently-reasoning model in the loop that's actually willing to check, not a structural guarantee that catches this specific class of failure every time. By using the Messages/ folder as a shared record, every interaction stays auditable after the fact, which is exactly how this error was caught — but auditable-after-the-fact is not the same as prevented-in-the-moment. Both matter. Only one of them exists right now.
