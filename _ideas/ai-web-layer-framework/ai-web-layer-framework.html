AI-Readable Web Layer Framework

A framework for giving AI systems a controlled, sanctioned path into a university website — rather than leaving them to scrape, guess, or go without.

Status First Draft Complete
First built June 2026
Sector Higher Education
Collaborator Claude (Anthropic)

The Problem This Solves

Most university websites block AI crawlers — for entirely legitimate reasons. Bot traffic inflates analytics, consumes bandwidth, risks licensed content exposure, and creates denial-of-service vulnerability. So IT teams block it, often by default.

The consequence is that when a prospective student asks an AI system about a university, the AI either can't answer accurately, pulls outdated scraped data, or fabricates details. The institution loses control of its narrative at exactly the moment a student is making a decision.

The argument to an IT or web team is not "let AI in." It is: give AI a designated, controlled path — so you can keep blocking everything else, preserve clean analytics, and control exactly how your institution is represented.

The Three-Tier Architecture

This framework is the second tier of a three-tier system. Each tier serves a distinct purpose:

Tier 1 — Marketing OS internal · university-agnostic
Source of truth for positioning, personas, value proposition.
Same intellectual work, facing inward — toward teams.
Tier 2 — AI-Readable Web Layer Framework this framework
De-identified methodology. Templates any university can implement.
Shows how to surface the Marketing OS externally, toward AI systems.
Tier 3 — Reference Implementation UNE · worked example
UNE prototype: 17 files, both layers fully populated.
Demonstrates the framework working in practice.

The connective logic: Marketing OS generates the strategy → Framework shows how to surface it externally → Reference implementation demonstrates it done. The same intellectual work faces two directions — inward to internal teams, outward to AI systems.

The Two-Layer Architecture

The AI layer itself is structured in two distinct layers with different purposes, different update frequencies, and different governance requirements:

ai.[youruniversity].edu.au/
├── llms.txt ← AI entry point
├── content/ ← what the institution is
├── about/
├── study/courses/
├── research/
├── campus-life/
├── international/
└── current-students/
└── skills/ ← how AI should talk about the institution
├── positioning.md
├── personas.md
├── usps.md
├── competitors.md
├── tone-of-voice.md
├── objections.md
└── faq.md

The content layer is the library. The skills layer is the librarian who knows how to use it. Without the skills layer, AI systems can answer factual questions accurately. With it, they can give genuinely useful guidance — acknowledging trade-offs, matching students to the right offering, and communicating in the institution's voice.

Hosting Architecture

The AI layer is hosted as a static subdomain — separate from the main website entirely. This is deliberate.

A subdomain like ai.youruniversity.edu.au is fully decoupled from the main site's infrastructure and security settings. It can be stood up as a plain static site (GitHub Pages, Netlify, Cloudflare Pages) without touching the CMS, without reconfiguring Cloudflare, and without impacting main site analytics. The main site's llms.txt points AI systems to the subdomain — everything else stays blocked.

The domain authority matters too: AI systems can verify that ai.youruniversity.edu.au is official institutional content, not a third-party interpretation.

Maintenance Model

The two layers have fundamentally different update profiles and should not be maintained the same way.

Content layer — operational
Updated each trimester or on page publish. Automated script or CMS export. No sign-off required.
Skills layer — strategic
Updated when strategy changes. Ideally an authorised agent drawing instruction from the Marketing OS.
Human sign-off required before deployment.

The Marketing OS is the upstream source of truth for the skills layer. When positioning or personas are updated in the Marketing OS, those changes propagate to the skills layer — not the other way around.

Connection to the llms.txt Standard

This framework aligns with the emerging llms.txt standard — a real convention proposed in 2024 and adopted by a growing number of websites as an AI-readable equivalent of robots.txt. The framework extends that concept with a full content and intelligence architecture rather than a single index file.

Implementing this positions a university as a genuine early adopter — and one of very few Australian universities with a deliberate, governed AI access layer.

Who This Is For

Any university that wants to control how AI systems represent it to prospective students — rather than leaving that representation to whatever an AI can scrape, infer, or hallucinate from outdated sources.

The framework is sector-specific to higher education, but the architecture — a controlled static subdomain, a content layer, a skills/intelligence layer, and an upstream strategy source — is transferable to any organisation that needs to govern its AI representation.
