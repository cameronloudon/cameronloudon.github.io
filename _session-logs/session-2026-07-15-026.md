## Thread 1 — Open Decision #57 Built: `generate-index-entry.ps1`

**What happened:** Cameron asked what was next on the list; the three genuinely open decisions (#48, #56, #57) were surveyed, and #57 stood out as the most shovel-ready — proposal drafted and independently reviewed back in session-60, only Cameron's own build-or-hold call left outstanding. Before recommending build, Cameron asked whether #57 interacted with the `_messages/` bundle-table compression from the prior session. It did, in one specific way: `index.md` had gone from "one of two places this is tracked" to "the only place," raising the stakes on keeping its entries accurate — though not changing the recommendation to build #57 as originally scoped, since completeness-checking (whether an entry exists at all) is a different concern from entry-line correctness (what #57 actually does). Sent this reasoning to Cowork as a formal consensus request. Her independent read agreed on scope, sharpened the causal framing (the gap isn't new, `index.md` just lost an informal cross-check that used to exist alongside it), and recommended the completeness question get its own numbered Open Decision rather than a footnote inside #57's own text, citing the #56→#58 precedent. Converged; Cameron authorized both directly: "build #57 now," #61 opened as tracked-but-unscheduled.

Built `_ai-context/generate-index-entry.ps1`: reads a single promoted file's frontmatter (`type:`/`title:`/`from:`/`to:` or `participants:`/`refs:`/`thread_number:`/`subgroup:`/`note:`) and assembles `index.md`'s established one-line entry format to console only — never writes to `index.md` directly, matching the deliberately small scope from session-60 (thread placement, sub-group headers, editorial framing, and the Gaps section all stay entirely hand-composed). Fails loudly on missing `type:`/`title:`/`refs:` or an actor field; warns rather than fails on missing `thread_number:`/`note:`, since those are new fields a file can still be usefully indexed without. Refs resolve to each target's own `title:`, rendered as a plain list rather than an attempt to reproduce the more editorial connective prose real entries sometimes use — documented as a known, deliberate limitation rather than passed off as a perfect match. Kept the script's own source pure ASCII (verified via a direct non-ASCII character scan, zero hits) — same precedent `function-b-state-check.ps1` set for the Windows PowerShell 5.1 non-ASCII-source parsing bug — while still producing output with the real em-dash/arrow characters `index.md` actually uses, built from character codes at print time rather than written literally in the source.

Tested against real promoted files before being trusted, not just synthetic fixtures: a `from:`/`to:` file with one resolvable ref, a `participants:` transcript, and a no-refs thread-opener, all producing output matching the real `index.md` lines' structure (refs rendered as resolved titles rather than the original's shorter editorial phrasing, as documented). Separately, against synthetic fixtures built in the scratchpad: all three fail-loudly conditions (missing `type:`, missing every actor-field shape, no frontmatter block at all) and the full happy path with every optional field present, confirming the placement hint, `note:` rendering, and unresolved-ref labeling all worked as designed. Fixtures deleted after testing.

Documented the two new optional frontmatter fields (`thread_number:`/`subgroup:`) and the new `note:` field in `messages-promotion-procedure.md` §2 (forward-only, same drafted-at-promotion-time authorship rule as `aliases:`), and the script's role/scope boundary in §6.

**Decisions made:** Build #57 as originally scoped, no widening. `thread_title:` (mentioned in the original proposal's phrasing) deliberately not implemented as a separate field — redundant with looking up the thread number directly in `index.md`, and the whole point of "human decides placement" is that a human is already looking at the file to place the line.

**Unresolved:** None for #57 itself — closed.
