## Thread 1 — Draft Agent HTML failures → content/HTML boundary decision

**What happened:**
Cowork raised two problems via the Messages folder handoff: (1) `draft-agent-config.md` hardcodes a section-specific structure template path, making it non-portable beyond `_ideas`; (2) the Draft Agent (Gemma 4 via Open WebUI) had failed six consecutive attempts at HTML generation — specifically scoping a div wrapper across child elements and omitting unmapped sections — while remaining reliable on content: topic, facts, voice, section identification.

Cowork proposed splitting responsibility: Draft Agent produces structured content only (no HTML, no frontmatter); Publish Agent converts to HTML using the appropriate template. Claude Code reviewed both the current role definitions (`AI_INSTRUCTIONS.md` §3) and the existing template library (`_ai-content-creation-spec.md` §6, already content-type-agnostic and complete) and recommended adoption — noting that the split isn't a workaround for one model's limitations but a correction of an accidental overlap: Publish Agent already owns "makes all repo changes" and the template library, it was just exercising that ownership by patching agent-authored HTML instead of authoring it directly.

Claude Code also identified that adopting the split resolves the first problem (Q1) as a side effect: once Draft Agent never produces HTML, it no longer needs a structure template — only a `content_type` field and the corresponding required-field list, which is portable across sections by construction since it's just the existing template library read differently.

Cameron reviewed the proposal (in the Messages exchange) and confirmed adoption of the content/HTML split as the canonical workflow, not a single-model workaround.

**Decisions made:**
- Draft Agent output format: structured Markdown with a plain key:value header (`content_type`, `title`, `permalink_slug`, `description`, `eyebrow`, and content-type-specific fields) plus `##`-heading sections. Not Jekyll frontmatter — this file is never committed as-is.
- `content_type` (`idea` | `signal` | `skill` | `standalone`) is set in the brief Cameron hands to the Draft Agent, carried through unchanged into the Draft Agent's output header — the Draft Agent does not infer or choose structure.
- Publish Agent selects the matching HTML template from `_ai-content-creation-spec.md` §6 based on `content_type` and authors all HTML/frontmatter from the structured content.
- `Drafts/` → `Ready/` → `Messages/` handoff mechanics are unchanged — only the payload format inside `Ready/` changes.
- Files updated by Claude Code this session: `AI_INSTRUCTIONS.md` (Draft/Publish Agent role descriptions rewritten to state the content/HTML boundary; new paragraph declaring the boundary canonical for any tool filling either role), `CLAUDE.md` (one paragraph added under Two-Agent System), `_ai-context/single-ai-workflow.md` (note that the split is optional for a single AI holding both roles, since it exists to solve a cross-model handoff problem), `_ai-content-creation-spec.md` (one sentence declaring §6 the single shared template library for both roles).
- Files explicitly left to Cowork/Cameron, per permission boundaries: `AI-Working/Protocols/draft-agent-config.md` (remove hardcoded template path and HTML-shape instructions; replace with the `content_type` → required-field table and the new output format) and `AI-Working/Prompts/publish-handoff-template.md` (add `content_type` as a required field; replace HTML-shape self-check items with content-level checks). Claude Code does not have read/write access to `Protocols/` or `Prompts/` by design (2026-07-02 permissions decision) and did not attempt to read or edit either file.
